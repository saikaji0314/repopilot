## 2. 重要进展和失败

### validation：补齐旧缺口，但不能照单全收

本次验证明确写出“POST /create 空标题时，post 表记录数不增加”。上次缺失的 `verifies_no_insert` 已补齐。

风险段却称 `not title` 会拒绝纯空格字符串。实际 `bool('   ')` 为 True、`not '   '` 为 False；该判断仍允许纯空格。此事实已用本地 Python 核实。不要直接采用建议去增加 strip 行为，因为纯空格处理需求尚未确认。

### config：有限恢复正确停止，但未恢复成功

第 3 步回复“说明文字 + JSON”，不满足纯对象协议。第 4 步为格式恢复，返回 `[{...}]`，虽是合法 JSON，却是数组；BaselineAnswer 校验报 `input_type=list`，最终 `invalid_final_answer`。

恢复后的文字补上了精确 DATABASE 路径断言，但这不能替代协议有效性。保留失败、不自动拆数组、不无限重试。是否增加确定性格式归一化，应另作设计与测试，不能事后修改此次成绩。

### ordering：不是本次正则误用，而是过度取证

本次先把 `-q -p no:cacheprovider` 放进 test_target，被拒绝后正确重试。之后已有查询代码、数据、模板和失败测试，仍继续调查。最后使用的 `ORDER BY` 是正常字面搜索；不要套用上次 `SELECT.*FROM post` 的失败原因。

在已用 10 次工具之后，第 7 个模型步骤还请求两个搜索，两者未执行。停止原因是工具次数上限，不是超时。模型两次声称已有全部证据，仍继续请求工具，是第二期调查效率/收尾策略的开发案例。
