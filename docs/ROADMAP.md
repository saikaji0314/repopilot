## 2. 推荐顺序和里程碑

以下按交付物和验收条件划分里程碑。每次只推进一个可解释、可测试的改动；需要缩小范围时先削可选项，不削审批与安全边界。

| 阶段 | 主交付 | 离开本期的条件 |
| --- | --- | --- |
| 第 1 期收尾 | 新批次严格评分、失败复盘 | 4/6 已达；作者理解自检仍需自己完成 |
| 第 2 期：检索与上下文 | 文件/符号索引、上下文选择、8 题对比 | 找证据和答对分别计分；较大仓库有可解释改善 |
| 第 3A 期：审批后小补丁 | CLI 审批、隔离工作副本、diff、实际测试 | 未批准不可写，至少 2 个端到端修复 |
| 第 3B 期：持久化与 API | SQLite、状态机、FastAPI、恢复 | 重启从安全节点恢复；不重复写入；拒绝/重审可用 |
| 第 4 期：评测与可靠性 | 至少 12 个独立样例、评分报告 | 一条命令可复现；失败/环境异常/费用不漏报 |
| 第 5 期：作品化 | 最小页面、README、视频、设计取舍 | 2～3 个可复现 Demo；新环境能照文档启动 |
| 缓冲 | 端到端排障与理解补课 | 不再新增大功能 |

3A/3B 是原第 3 期内部拆分，分别验证受控写入和持久化服务，避免一次同时引入写入、状态机、数据库和 Web API。

## 3. 第 2 期具体怎么做

不要先安装向量数据库。先回答：“哪里因为没找到代码或上下文浪费而失败？”ordering 就是现成的起点。

1. 记录当前搜索的字面匹配语义，补清晰描述和简单测试；需要正则时独立显式参数，不悄悄改变旧接口。
2. 用文件路径、Python AST 的函数/类名、行号做轻量索引；保留关键词搜索。索引只扫描允许范围，不包含密钥、运行产物、虚拟环境或 Oracle。
3. 为工具结果做去重、片段选择、字符预算和来源标注；提示被截断、提供继续读取方式。不要一上来做模型摘要记忆。
4. 扩展到至少 8 个独立任务，其中新增题用于较大上下文/跨文件取证；先通过环境预检。选择一个可信、依赖简单、无需硬件的稍大样例，先审批范围再接入，不直接拿任意 GitHub 仓库执行测试。
5. 固定相同模型/预算，对比旧检索与新检索：关键证据命中率、读取量/重复率、严格任务通过率、费用。较大仓库样例不能只在新版上跑。

验收保留原要求：不仅能引用行号，还要记录一个误检/漏检案例和可解释改善。如果没有收益，如实标记未证明，不因“用了 AST/RAG”就算验收通过。

作者需要理解：检索相关不等于事实正确；返回空结果不等于代码不存在；上下文预算与模型总 Token 预算是两件事。第一步先写输入输出契约与 3～5 个小测试，再实现索引器，不动整个 Loop。

## 4. 第 3 期具体怎么做

### 3A：先在 CLI 做闭环

只在复制的任务工作区中改源码，不改主样例和用户原仓库。建议先做受控补丁接口，不给通用 shell，也不让模型安装包。

- 分析输出建议 → 生成候选 diff（此时不应用）→ 展示 diff/文件范围/验证计划 → 用户批准 → 应用 → 测试 → 报告。
- 批准应绑定计划版本、补丁内容和目标文件原始摘要；变更范围或补丁变了需重新批准。
- 代码校验权限，不能只依赖 system prompt。拒绝越界路径、敏感路径、测试/Oracle 篡改，以及超出批准范围的文件。
- 先修复路径解析、超时执行和保存脱敏这些与新能力直接相关的前置缺口；固定可信样例不等于任意代码执行沙箱。
- 用两个简单 Flaskr 缺陷做闭环；分别记录修复前失败、修复后目标测试通过、回归通过、实际 diff。
- 验证失败先保留现场和报告，不自动无限修到成功；第一次可仅允许一次补丁尝试。

作者需要理解：模型建议与宿主授权的区别；测试返回失败与工具执行失败的区别；分析答案正确不等于实际补丁正确。

### 3B：再保存与恢复

持久化任务、状态、审批版本、步骤、消息、工具结果、补丁摘要。先单任务串行、SQLite，不增加 Redis/Celery。

新增工作流层，不把现有一次 Loop 的结束状态直接当整个业务生命周期。状态包含分析、等待审批、应用、验证、完成、失败、拒绝等，明确允许的转换。

优先接口：创建、查询、批准/拒绝、修改计划后重审、恢复。测试“等审批时重启”“应用成功但保存结果前中断”等情况；遇到是否已写入不确定时核对工作区摘要，不能盲目重放副作用。宣称可恢复必须说清支持哪些安全节点。

## 5. 第 4～5 期：证明效果并做成作品

第 4 期扩到至少 12 个独立任务；同一题跑 12 遍不是 12 个样例。当前 6 题已反复调试，视为开发/回归集；新增题预先固定并留出一部分不用于调提示词，记录何时解封。

评分分层：

- 协议层：是否正常终止、结构正确、恢复几次。
- 分析层：根因、证据、修复建议、验证完整性；保留现有 Oracle。
- 修复层：diff 能否应用、目标故障是否消失、已有回归是否仍通过、有没有越权改动。
- 成本层：所有尝试的 Token、时间、估算费；环境失败单列，不能从总尝试数悄悄删除。

确定性评分优先；LLM 裁判只辅助开放式文字项，作者抽查。不要把旧“分析通过率”和新“实际修复率”混成一条曲线。全局 12 题至少 70% 的目标应先冻结口径：若 12 题均为修复任务，至少 9 题严格修复通过；若混合题型，分别报告，不用分析题冒充修复成功。

冻结代码、提示词、工具定义、模型参数、任务版本、费用单价和运行配置快照。每次实验只改变一个主要因素；当前版本没有优于基线也应展示，这是工程判断，不是项目失败。

第 5 期最小页面只需任务输入、审批、进度和报告/Trace；先用已有 API，避免前端重写业务。准备成功修复、拒绝审批、预算/验证失败三个演示角度。密钥和原始对话脱敏后再公开；视频 3～5 分钟。项目说明应描述具体实现和真实结果，不写“达到工业级”或未经测量的提升百分比。

## 6. SWE-bench 放在哪里

**结论：与长期方向匹配，但不适合作为当前只读第一期的替代验收。** 它衡量根据真实 GitHub 问题生成补丁，并通过测试判断是否解决；不是评判一段根因分析文字的题库，也不是必须采用的 Agent 框架。官方标准评测使用 Docker 环境。见 [官方 FAQ](https://www.swebench.com/SWE-bench/faq/)。

Lite 有 300 个测试任务及 23 个开发实例；“Lite”表示评测集合较小，不代表每道题对初学者都简单。见 [Lite 官方说明](https://www.swebench.com/lite.html)。

建议作为第 4 期之后的可选外部验证支线：

1. 先完成受控写入、真实测试、路径/执行隔离；检查本机容器支持、磁盘和依赖下载成本。不在本轮安装任何环境。
2. 从 Lite 开发集预先选 3～5 题，只先跑 1 题环境预检，记录选择原则和失败原因；这属于开发冒烟，不能称为完整 SWE-bench 成绩。
3. 对齐 `repo`、`base_commit`、`problem_statement`，输出 `instance_id`、`model_name_or_path`、`model_patch`；不要直接复用当前 final_answer 作为提交结果。
4. 参考补丁、评测补丁、FAIL_TO_PASS/PASS_TO_PASS 清单仅供评估端，不提供给解题 Agent。前者检查故障被修复，后者检查已有能力未回退；见 [数据字段说明](https://www.swebench.com/SWE-bench/guides/datasets/)。
5. 预算与环境可承受时再固定 10～20 个未调试的测试实例做小样本外测。报告明确写“自选子集、样本数量、配置”，不和完整榜单直接比较。

本地主线 Docker 仍可选；选择官方 SWE-bench 评测这条支线时，Docker 是该评测的前提，不意味着要部署公网。不支持或准备耗时过长就暂停支线，自建评测仍能完成作品目标。

不要现在就跑全套 300/500 题、换掉整个主仓库、照搬完整 SWE-agent，或为了榜单引入多 Agent。官方基准的外部有效性也不能只靠几道手选成功题证明。

## 7. 预算和开发方式

总 API 上限仍为 ¥200。已知基线报告约 ¥0.38、当前批次约 ¥0.47，并非全部历史花费；先核对百炼账单，不能据这两个报告声称还剩 ¥199。

建议未来开发+里程碑评测设 ¥100 软上限，最后回归/演示预留 ¥40，SWE-bench 支线最多 ¥20～30，其余缓冲；所有额度同时受实际剩余预算约束。支线先实测单题费用再决定扩样，不承诺预算能覆盖完整基准。容器下载、磁盘和排障时间另外考虑。

继续采用“小步手写核心机制 + AI 审查与补测试”：

1. 自己写半页契约/伪代码，标出成功、失败和副作用。
2. 先写已确定行为的简单测试；未知边界在探索后补测试，不为追求 TDD 形式而写大量内部实现断言。
3. 一次只实现一个模块；让 AI 解释和审查，不一次生成下一整期。
4. 每个里程碑自己读一条成功 Trace 和一条失败 Trace，写下为什么调用/停止。
5. 只在行为和测试稳定后整理代码；理解债优先于堆框架。

下一次实际工作：按第二期步骤 1 明确现有搜索契约，补小测试与对应实现，再进入索引模型。本文是后续计划，不代表已经执行外部下载、付费跑批、写入工具或框架替换。
