# 双视角审核、发现合并与争议复核

更新：2026-10-28。范围：M5 的固定审核快照、正确性／需求上下文两个只读视角、发现证据结构、去重与阻断规则、最多三次修改、按需 A／B＋C 争议复核、人工争议出口以及审核依据的失效与复用。本文只描述本地机制；真实模型双审效果、Docker 双审和真实平台交付仍未验证。

## 一轮正式审核是什么

一轮正式审核包含两个**并行、首轮上下文独立**的只读视角：

| 视角 | 重点 | 共同输入 |
| --- | --- | --- |
| `correctness` 正确性与回归 | 边界、调用方、回归、实现错误、检查事实 | 同一固定提交与基线、同一差异、同一份独立重跑检查、同一确认资料和任务说明 |
| `context` 需求与业务上下文 | 原 Issue／需求、人工答复、验收、确认决定、项目约定；也可读代码 | 同上 |

两个视角在首轮都看不到实现方的自我说明，也看不到对方的发现。它们可以自行读取源码、调用已登记检查，但不能修改文件。复审轮次会拿到上一轮固定ID的发现和处理证据，仍不要求两份报告结论一致。

审核绑定一份**依据快照**：候选提交、基线提交、独立检查摘要、资料清单版本、任务说明版本、计划版本、需求答复版本和返工次数。任何一项变化都会产生新的依据哈希；旧审核与旧批准不能继续代表当前代码和需求。

## 发现的结构与合并

每条发现至少包含：

- `severity`：`blocker`／`major`／`minor`；
- `evidence_status`：`reproduced`（复现过）、`source_inference`（有源码依据的推断）、`insufficient_information`（证据不足）；
- `requirement`、`trigger`、`impact`：违反的要求、触发条件和实际影响；
- `observation`、`suggestion`：观察和可执行建议；
- 依据位置：代码问题用 `basis=code` 给出实际读到的相对路径与起始行号；需求／验收缺口用 `basis=requirement`／`missing` 和 `reference`；检查失败用 `basis=check`；资料依据用 `basis=material`。缺失行为不要求编造行号，反之非代码发现不允许硬塞代码位置。

程序按“依据位置＋观察文本相似度”合并两个视角的同一问题，保留双方原始措辞和来源；互补发现不会被合并或当成争议。每条合并发现获得稳定ID（如 `r1-f1`），复审必须逐条回应这个ID。

### 阻断规则

| 情况 | 处理 |
| --- | --- |
| `blocker`／`major` 且证据不是“信息不足” | 阻断，进入返工或争议复核 |
| `blocker`／`major` 但证据不足 | 不能批准；带问题进入集中提问，没有具体问题时停止为`review_inconclusive` |
| `minor` | 只记录为非阻断建议，不能仅凭偏好阻止批准 |
| 任一方漏答、`unable_to_verify` 或只给信息不足 | 不关闭发现；保留为待补证据，不能批准 |
| 两人都声称已解决但都没有可核对证据 | 不关闭发现；保留为待补证据，仍不能批准 |
| 复审重报旧发现、同时一方坚持未解决 | 先去重并保留原发现ID，再按双方证据判定争议；重报不能吞掉冲突 |
| 独立登记检查未全部通过 | 程序强制否定批准，即使两个视角都说通过 |

两个视角都要求修改时，程序按上述规则合并；报告仍保留各视角原始结论和问题，不会为了“让报告看起来一致”改写它们。

## 返工次数与交接

初审之后最多 **3 次修改＋复审**，共最多 4 轮正式审核；两个视角共同算一轮，不按 Agent、子任务或平台对象分别计数。每次返工只带程序认定的待修发现，修复一批算一次修改。

到限后状态为`rework_limit_reached`，同时打开`handover`人工请求，列出未解决发现、证据、已用次数和可选择的下一步。负责人可以：

1. 补充需求／业务信息后`resume`（会重新规划，历史计数保留）；
2. 用`repopilot review continue RUN_ID --extra 1 --reason "..."`明确增加修改额度，次数和历史保留；
3. 用`retry`开始新尝试（旧运行与旧计数仍可回查，累计费用沿用原账本）。

不会因为换角色、换子任务、重启或恢复而自动清零。

## 具体争议才触发 A／B＋C

只有**真实反证或互相冲突的判断**才触发额外复核：复审时一方给出有依据的“仍未解决／不是问题”，另一方给出有依据的相反判断。互补发现、一般分歧或“审核者不喜欢”不触发三人复核。

1. A、B 获得两个新的独立上下文，只看同一固定版本和同一争议，不看对方结论；每侧结果完成即落盘，恢复只补缺失的一侧，C 只在两侧齐备后执行；
2. C 比较 A／B 证据，必要时用登记检查复现，输出`confirmed`、`refuted`或`undetermined`；
3. `confirmed`→发现继续阻断并返工；`refuted`→排除该发现并记录理由，其他发现继续处理；`undetermined`→打开`dispute`人工请求，状态`needs_input`。

同一提交、同一实质依据中的同一发现最多启动一次 A／B＋C；同提交同实质依据的恢复可直接复用已完成结论。实质依据包括候选提交、基线、独立检查、资料清单、任务说明、计划和需求版本；单纯返工计数变化不重开争议。**更换提交或实质依据后，旧结论只作历史，不能自动排除新候选上的同名发现**：新候选再次出现有依据的冲突时重新核对一次（每个提交最多一次），而不是把过期的人工排除或确认套到当前代码。C 的`refuted`不等于整份代码通过，其他发现和独立检查仍要处理。

```powershell
repopilot review show RUN_ID --output .local/runtime
repopilot review decide RUN_ID --dispute d-1 --decision confirmed|refuted --reason "核对证据后的判断" --output .local/runtime
repopilot review continue RUN_ID --extra 1 --reason "负责人同意再改一次" --output .local/runtime
```

`review show`、`review decide`和`review continue`不加载模型或平台凭证，也不调用模型。`review decide`必须是登记负责人对具体争议的明确判断，普通`human answer`不能代替它；争议判断也不等于交付批准。判断后仍需`resume`才继续执行。

## 依据失效与结果复用

- 人工答复、资料变化或明确刷新会记录失效原因，撤销旧检查结果、旧审核和旧批准；历史轮次保留，不删除旧证据。
- 同一提交、同一依据再次进入审核（例如审核完成后、写出结论前进程退出并显式恢复）时，直接复用已完成轮次，不再调用审核模型；报告标记为复用并保留原依据哈希。
- 新的提交、新的任务说明、新的资料清单或新的检查结果都会产生新依据，不能复用旧结论。
- 批准摘要包含审核依据、合并发现和争议结论；需求、代码或证据变化后旧批准在发布前失效。远端默认分支变化仍由发布前的只读核对发现。

## 恢复与证据

- 启动审核前先保存依据快照；每份完成的视角报告立即落盘，恢复时只补未完成的视角。
- 合并后的发现作为草稿保存；A／B、C 的结论逐条写回后，才形成最终轮次记录。中断恢复后不会把旧轮次的同ID发现混进当前轮次。
- 争议去重使用不含返工计数的实质依据哈希；只增加返工次数不会重开同一提交上的同一争议，提交、检查、资料、任务说明、计划或需求版本变化才会产生新的争议记录。
- 旧记录没有实质依据字段时，未决争议查找与结论复用采用同一受控回退：仅当完整依据哈希也相同时才匹配；升级恢复后仍会生成可供`review decide`处理的请求。
- 每轮保存`review-<perspective>.json`、`review.json`和完整的`review_rounds`／`disputes`；报告展示视角结论、发现依据、证据状态、争议A／B／C和修改次数。
- 等待人工判断或到限交接期间不占用模型执行；恢复、费用和计数沿用同一运行。
- 旧运行没有M5审核字段时，恢复会补默认记录但不删除历史；旧运行的原批准摘要算法保持不变，仍可按原摘要批准。新运行使用包含审核依据、合并发现和争议结论的摘要。

## 验证与限制

测试入口：[双审与争议](../../tests/runtime/test_dual_review.py)、[审核契约](../../tests/runtime/test_report_contract.py)、[原有审核循环](../../tests/runtime/test_review_loop.py)。使用确定性审核／A／B／C报告替身与真实本地 Git、SQLite、工作区和 CLI，覆盖首轮上下文独立与并行、互补发现合并、同一问题去重、非阻断建议、证据不足不批准、复审漏答／无法核验不能关闭、重报旧发现不吞冲突、三次修改与交接、人工延长、同一依据复用、新候选争议重新核对、A／B单侧完成后恢复、争议触发与三种 C 结论、人工争议判断、依据失效和报告展示。

M5机制增量未验证的范围如下；M6已补充真实模型双视角到固定SHA批准后的草稿交付，结果及执行后端边界见[增量30](VALIDATION-30.md)。历史机制测试与新增真实结果分别计量：

- 没有真实模型作为两个审核视角或 A／B／C；测试报告由确定性替身返回，不能说明模型发现缺陷的效果或双审收益。
- 没有真实 Docker 后端的双审并行；每个视角会各自创建只读容器会话，该组合尚未实测。
- 没有真实 GitHub／GitLab Issue 评论争议往返；`dispute`／`handover`当前只走本地 CLI。
- 去重是位置加文本相似度的保守规则，可能把措辞差异很大的同一问题分成两条，也可能在相邻行合并不同问题；仍由人核对最终证据。
- 争议复核只覆盖“复审回应冲突”，不把任意自然语言分歧都自动升级为三人复核；A／B／C 判断质量依赖模型和证据，不能保证语义正确。
- 审核依据复用只限同一提交、同一依据，不跨运行或跨重试复用。
