## 上下文改了什么，为什么再修正

旧机制只清理读取输出，assistant／工具参数及必须回传的reasoning仍增长；新基线19254仍触发context_bytes。首轮从真实工具结果维护小型工作集，保留任务和最近完整工具轮次，在65%阈值替换请求视图。

这过于积极：成功基线20212最高输入仅62194字节，本来未逼近90 KB上限；首轮改进却触发16次压缩。压缩只存在于请求视图，下一轮重新从完整旧历史裁剪，容易反复丢失调查上下文。首轮虽有补丁通过验收，但没有证明这种策略改善交付。

修正后阈值为消息预算90%，在响应后用LangGraph消息reducer保存已发送的压缩视图及当前全部响应，后续工具消息继续追加。同题修正组只触发一次压缩。保留的assistant含reasoning字段原样，不切断并行工具配对；工具结果仍留本地事件。没有额外摘要模型调用，没有将源码片段提升到系统提示。具体行为与代价见[上下文协议](CONTEXT.md)。

这仍是阶段内源码观察工作集，不能保留全部语义推理；它不是LangGraph数据库checkpointer，也不是跨运行的仓库记忆。全局调用和审核仍竞争同一额度，本轮多个正确候选没有走完审核，阶段收尾空间仍需独立设计与验证。

## Docker执行故障与诊断

修正轮19254的开、关两格均在压缩触发前遇到`docker_exec_failed`，各自空补丁保留，未自动重跑。按原15个只读工具步骤分别顺序重放、按原批次在线程池重放均通过，且未调用模型。历史Docker事件不足以还原原因，因此没有证据把故障归因WSL、OOM、并发或上下文代码。

原传输层仅暴露固定错误码，清理后诊断不足。本轮增加RPC错误事件，保存操作、返回码、固定分类和输出字节数，仍不记录stderr正文、命令、路径或认证内容；超时、失败不回退本机、不重试模型。该改动改善可观测性，**不是已修复那两次执行故障**。
