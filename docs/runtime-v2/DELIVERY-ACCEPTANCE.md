# 新流程的交付验收

M6验证从需求、资料、计划、实现、双审到人工批准与草稿交付能否连起来。机制测试和真实效果分别登记；通过本地测试不能替代真实GitHub交付。

报告、组合验收和本轮真实任务的分阶段结果见[增量30](VALIDATION-30.md)。实跑已纳入通过独立复审的M5最终修订。历史[Issue #1交付](VALIDATION-05.md)使用旧流程，不能当作本轮新成绩。

## 开始前固定什么

每个实际任务先登记：

| 项目 | 必须能核对的内容 |
| --- | --- |
| 新需求 | 原Issue及平台、host、项目、编号；目标、验收、范围外事项 |
| 代码与依据 | RepoPilot提交、目标基线、所用资料ID与版本；前序修订先整合再冻结 |
| 环境 | 解释器、依赖、检查argv、执行后端、远端只读能力预检；未准备的环境单列 |
| 额度 | 包括规划、实现、双审、三次修改和可能争议复核的调用、费用及活跃时间上限；沿用累计账本 |
| 外部动作 | 需要的Issue、集中评论、必要子Issue和最终草稿PR；不把回答问题视为交付批准 |
| 独立验收 | 开始前列出的行为检查与命令，执行者、结果、实际人工贡献；不得事后改验收让候选通过 |

实际仓库按已确定的顺序执行，先完成较小任务，再进入较复杂项目。允许单Agent或顺序计划；是否并行由计划解释，不为演示强制拆分。并行与争议等不一定自然出现的分支先用可控场景覆盖，真实运行未触发就如实记录。

独立验收的具体失败语义也需写进可信任务要求，例如“任务存在但结果文件缺失返回404”，避免只写“明确失败”而让机器任务说明补成另一状态码。可用`--stop-after plan`先核对派生任务说明／计划与原始需求、独立检查，再显式`resume`。机器假设及两位审核者的一致判断都不能替代负责人确认；M6实际记录过检查与派生计划口径冲突而未能交付的情况。

[小型任务候选profile](../../examples/runtime/full-delivery-acceptance.yaml)把规划、实现、双审、修改与争议共计限制为80模型调用、200工具调用、50编辑、3次修改、3600秒活跃时间和20元估算费用。它只提供可校验参数，具体任务的充分性、累计余额和外部动作仍须在批次登记中核对；不自动提高原账本或触发运行。

## 从接入到交付

先使用[平台接入](FORGES.md)登记的本地任务模板与执行profile接入新Issue。新运行默认规划；检查命令来自可信模板。资料登记与确认见[项目资料](KNOWLEDGE.md)。

```powershell
repopilot issue ISSUE_URL --task TASK_YAML --profile PROFILE_YAML
repopilot status RUN_ID
repopilot human list RUN_ID
repopilot plan show RUN_ID
repopilot review show RUN_ID
repopilot report RUN_ID --html REPORT_HTML
```

实际运行使用同一输出目录；更换目录不能变成规避累计费用或重复创建工单的方法。上面的占位符需替换成已登记值，命令不代表授权真实发送或模型费用。

需要澄清时先查看当前请求，再通过父Issue评论或本地CLI答复。评论渠道须只读预检并登记负责人，等待期间不继续调用模型；导入有效答复后显式恢复。答复与请求版本、来源、代码和资料版本一起保存。详见[人工协作](HUMAN.md)与[规划](PLANNING.md)。

候选完成后，核对组合差异、真实检查退出码、双审发现、争议处理和剩余建议。查看完整提交后再决定：

```powershell
repopilot approve RUN_ID --commit FULL_SHA --reason "核对需求、组合差异和检查后的理由"
repopilot publish RUN_ID
repopilot report RUN_ID --html REPORT_HTML
```

批准的是这个完整提交及证据摘要。代码或依据变化后需重新检查、审核与批准。发布失败先查保存的身份和远端，不删库重来；响应丢失的重试复用既有草稿。最终核对远端功能分支、草稿头与批准SHA一致，不合main、不部署。

## 报告如何回查

报告保留原有实现、检查、审核和审批区分，并补充：

- **当前等待事项**：谁需要决定什么、请求类型及受影响子任务或阶段。
- **版本与来源**：审核依据摘要、候选、基线、检查摘要、资料清单、任务说明和计划版本。
- **人工来源**：请求ID和版本、答复动作与身份、渠道、评论作者与链接、提问投递链接；无记录明确标注。
- **资料和决定**：来源、关系、确认状态；按决定记录的精确版本读取简短理由，保留来源入口。提议不成为确认要求。

正文通过SQLite只读连接读取，报告不建库、不迁移、不同步索引。正文位置从`runs/<id>`的所属运行根定位，与用于脱敏的源码根分开，所以CLI显式`--output`也能回查同一版本。缺库、损坏正文或原仓库不可定位时保留元数据并标注正文不可用，不替换为新版本。历史正文仍可由`knowledge read --id ID --version VERSION`分页核对；该管理命令与报告的只读读取入口不同。

报告是可离线打开的快照，不能证明监听器仍在运行；也不执行答复、批准或发布。分享前仍需核对业务内容。

## 怎么判断真实验收完成

| 条件 | 证据与限制 |
| --- | --- |
| 平台 | 新GitHub任务的Issue、评论／子Issue实际结果与草稿URL；GitLab按功能逐项写真实、离线或不支持 |
| 兼容 | 既有任务、监听、恢复、批准、报告及所选后端的相关回归；旧数据保留，新增只读报告不迁移库 |
| 可追溯 | 从原需求和人工答复串到计划、决定、固定候选、检查、两类审核、批准和草稿；当前阻塞可读 |
| 实际效果 | 任务、环境、额度和独立验收事先登记；模型完成、程序机制、人工修改分别报告 |

费用不足、环境故障、模型修复错误、审核误判和流程错误分别记录。失败尝试也保留，不只展示最好结果；不能以“有草稿URL”代替行为通过，也不能将一次双审或资料命中外推为收益提升。

## 实现取舍与阅读导航

报告继续组合既有SQLite检查点与版本化正文，没有新增一套“验收成功”数据库或额外模型裁判。完整链路使用`workflow`和`forge.publish`的实际入口；本地测试仅替换模型和平台，不绕开批准门。

| 阅读顺序 | 输入与输出、要理解的边界 |
| --- | --- |
| [组合验收](../../tests/runtime/test_delivery_acceptance.py) | 问题批次→持久化答复→顺序计划→组合检查→双审返工→批准→发布响应丢失后复用；另有实际检查失败不放行 |
| [运行生命周期](../../repopilot/orchestration/workflow.py) | `start/resume/decide`分别接任务、恢复和批准；业务答复不能替代`decide` |
| [发布](../../repopilot/delivery/forge.py) | `publish`先验批准摘要与基线，再核对远端分支及草稿，不重复创建 |
| [来源兼容验证](../../tests/runtime/test_source_identity.py) | 平台／host／项目／编号共同区分工单；同来源旧索引只迁移键，保留状态、批准、计数；未知来源保守交人 |
| [报告装配](../../repopilot/presentation/report.py) | `build/render`读取已有证据并组合页面；没有运行或审批动作 |
| [来源片段](../../repopilot/presentation/traceability.py) | `render`呈现状态中的版本与来源；`decisions`按记录版本取理由并处理缺失 |
| [只读正文](../../repopilot/knowledge/reader.py) | 复用既有正文散列验证与分页，以`mode=ro`连接避免报告触发迁移 |
| [报告验证](../../tests/runtime/test_traceability_report.py) | 同号跨平台显示、历史版本、不改旧库、缺失／损坏降级、HTML转义与链接约束 |

取舍：复用原正文校验，避免报告与资料工具各有一套版本算法；只读入口不执行可写Store初始化。单页只摘取前120行，完整记录仍在版本文件；这比把所有问答和原始日志自动打包更符合资料边界。更多阶段职责和替代方案见[架构](ARCHITECTURE.md)、[设计](DESIGN.md)、[双审](REVIEW.md)与[并行整合](PARALLEL.md)。
