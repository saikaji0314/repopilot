# 运行内上下文与仓库记忆

两者用途不同：运行内上下文帮助当前任务继续调查与编辑；[仓库记忆](MEMORY.md)跨运行提供人工确认的文件事实，不继承检查或审批结论。

## 为什么清理旧工具结果还不够

早期运行使用 LangChain `ContextEditingMiddleware` 清除旧读取结果，但它保留 assistant 消息、工具参数和供应商要求回传的 reasoning 字段。历史 19254 即使已有大量读取被清除，仍触及 90 KB 请求上限，见[失败轨迹](VALIDATION-18.md)。只提高上限或重复提醒“尽快修改”不能验证问题已解决。

## 有界请求视图

`agents/context.py` 从实际完成的工具结果维护最近观察：读取位置和带行号的有限片段、搜索命中及覆盖信息、编辑回执、检查退出码及输出尾部。最多十条、8 KB；编辑文件后丢弃旧文件片段和旧搜索结果。原始工具结果仍保留在本地事件中，进度随原有检查点保存。

每次模型请求先扣除系统提示与工具定义占用。消息接近剩余预算的 90% 时，尝试替换完整的旧工具轮次，保留：

- 原任务载荷，包括冻结的需求、检查名称和可用仓库记忆。
- 标为历史参考数据的工作集；片段可能截断或过时，编辑前仍须读取当前源码。
- 最近一至三个完整 assistant／tool 轮次，保持多工具调用配对和其 reasoning 字段原样。

工作集作为普通用户载荷发送，不放入系统提示，不提供新工具或权限。不生成、存储或展示模型的原始思考，也没有额外摘要模型调用。请求返回后，用 LangGraph 的消息 reducer 将压缩视图和本次完整响应保存到框架会话，后续工具结果继续追加，避免每轮重做同一压缩。本地事件与候选保留，调用计数和累计预算不重置。

若当前任务、工具定义或最近轮次本身过大，无法得到足够小的合法视图，就仍以 `context_bytes` 停止。配对不完整或出现无法安全改写的消息边界时不压缩。`context_compacted` 事件只记录前后字节数与移除消息数，不记录 reasoning 正文。

该机制是源码观察摘要，不是完整语义总结。旧推理和部分源码细节不再可见，可能引起重复调查或丢失有效假设，必须通过同配置真实复测评估。DeepSeek 在工具调用中对 reasoning 回传的要求见[官方协议](https://api-docs.deepseek.com/guides/thinking_mode/)；保留的 assistant 不删字段，旧轮次作为整体移出视图。

## 实验边界

[固定协议](../../evals/swebench/context-memory-20261019.json)分别比较新基线、上下文机制和仓库记忆开／关；各组使用相同预算配置。新配置增加调用和输出空间，故历史结果只作诊断，不能将与旧配置的差异归因于此机制。修复通过官方验收与完成独立审核分别计数，空补丁和超限均保留。

首轮65%阈值、只改请求视图的实验没有证明交付收益；[单独冻结的修正协议](../../evals/swebench/context-memory-refinement-20261019.json)改为90%并保存会话，追加四个固定单元，原九次全部保留，总费用估算仍受18元约束。不能将两轮最好结果拼接成成绩。
