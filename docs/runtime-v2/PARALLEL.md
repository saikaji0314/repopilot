# 并行实现、独立工作区与内部整合

更新：2026-10-28。范围：M4的可并行计划、最多2个实现槽位、子任务独立worktree、依赖基线、串行整合与组合检查。本文只描述本地机制；真实模型并行效果和真实平台交付仍未验证。组合候选的双视角审核与争议复核见[双审与争议](REVIEW.md)。

## 什么时候并行

规划报告新增`split=parallel`，与`none`／`sequential`并列：

- `parallel`至少两个子任务，且至少两个互不依赖；规划理由必须说明为什么这些子任务可以独立完成、修改边界不冲突。
- 程序仍按依赖拓扑排序；同时运行的子任务必须依赖已完成，并已**整合进父临时工作区**。
- 依赖下游的worktree基线是父整合工作区当前的HEAD，不是另一个worker正在修改的目录。
- 顺序计划继续走M3的单worktree路径；单Agent路径和无计划路径的执行语义不变，但同样计入全局实现槽位。

```powershell
repopilot run task.yaml --max-implementation-slots 2 --output .local/runtime
repopilot plan show RUN_ID --output .local/runtime
```

`max_implementation_slots`默认2、允许1或2；`--slot-timeout`控制等待空位的时间。槽位租约在`jobs.sqlite3`的`implementation_slots`表中，所有运行共享，不能靠同时接多个Issue把并发放大到2以上。并行worker、单Agent／无计划、顺序子任务、返工和整合修复Agent都必须先取得同一槽位；整合前会释放worker租约，再由整合修复取得自己的租约。进程退出后租约按TTL过期。

## 独立worktree与共享额度

每个并行子任务有自己的worktree，路径在运行目录`worktrees/<run>-<subtask>-<随机后缀>`，从父整合HEAD创建。worker只写自己的worktree并产生独立提交，不修改父状态、不直接发布。

各worker的模型调用、工具调用、Token、费用和检查记录共享同一`Quota`；父会话的检查点读取共享计数。线程局部保存阶段、进度和已读位置。工作区、编辑额度、预算账本和运行锁仍由父控制面统一管理。

## 串行整合

子任务完成后，父工作区按完成顺序逐个应用，而不是让每个worker各自创建PR：

1. 父工作区必须干净，HEAD等于当前整合提交；
2. 用`git cherry-pick --no-commit`应用子任务提交；
3. 干净应用后由父工作区提交“整合 <子任务>”并记录来源提交、基线提交、整合提交和worktree；
4. 普通冲突交给受控整合Agent，在父工作区保留双方功能并解释冲突原因；
5. Agent报告`resolved`后，程序仍检查未合并索引、冲突标记和提交是否真的产生；残留冲突或空整合都停止，不当作成功；
6. 涉及接口／业务取舍、缺少信息或无法可靠合并时进入人工请求，冲突现场先回滚到干净的整合HEAD，不能带着冲突标记继续审核或交付。

整合记录保存在`integrations`，报告显示来源提交、整合提交、处理方式和冲突文件。子任务结果里的`commit`是整合后的提交，`source_commit`保留worker原始提交，二者都可追溯。

## 最终检查与边界

全部子任务整合完成后才执行原有anchor、独立重跑全部登记检查、双视角审核、按需争议复核和人工批准；审核看到的是**组合后的固定提交**，不是各子任务自己的报告。子任务各自实现完成不等于组合通过，组合回归失败或整合冲突都不能直接交付。审核维度、发现合并和返工上限见[双审与争议](REVIEW.md)。

内部整合只发生在运行目录的临时worktree，不更新原仓库工作树、main或远端；仍只有一个父任务汇总草稿PR（M3的发布路径）。不会为每个worker自动创建PR，也不会因创建草稿自动关闭父／子Issue。

## 局部暂停与恢复

- 某个子任务需要澄清或整合冲突转人工时，只阻塞该子任务及其后继；其他独立子任务继续执行、提交并整合。父文件、独立结果和检查点都保留后，才汇总打开人工请求并进入`needs_input`。
- 受影响子任务的worktree和不完整报告保留在`parallel_runs`／`parallel_blocked`；未提交编辑不会自动续用，答复触发计划变化时按M3重规划，但已整合的独立提交不会被说成丢失。
- 整合操作在应用前写入`pending_integration`。冲突修复Agent抛异常或进程中断时，父冲突现场和来源提交保留；显式`recover`接纳现场后，恢复会继续同一整合，而不是要求先把工作树改干净或重放worker。
- 无冲突`cherry-pick --no-commit`已完成但尚未提交时，恢复会识别暂存区中的合法应用结果并直接完成整合；若应用尚未发生，则用`pending.source_commit`重新应用，同样不重跑已完成的worker。
- 普通异常回滚后才进入`needs_input`；已提交的整合由`pending_integration`识别并补记，不会重复提交。
- 进程中断且没有可接续的整合现场时，`parallel_runs`中的running记录标为`interrupted`，保留worktree；恢复按计划重新执行受影响子任务，但这只用于确实没有来源提交可接续的情况。
- 没有worktree或顺序计划仍使用原有阶段恢复；无计划单Agent和顺序子任务也申请槽位，槽位等待超时以`limit_reached`/`implementation_slots_busy`停止，不绕过上限。
- worker的工具和编辑尝试逐条写入`events.jsonl`；硬退出后恢复会从可靠事件重建被父检查点遗漏的共享计数。正在编辑的尝试先消耗额度，因此除明确的`edit_limit_reached`外，失败编辑也计入恢复，不由“成功工具数”代替。

## 验证与限制

测试入口：[并行与整合](../../tests/runtime/test_parallel.py)。使用确定性worker替身、真实本地Git／SQLite和运行目录，覆盖同时启动两个独立子任务、依赖等待已整合前置、普通冲突受控修复、冲突转人工、单槽位串行、槽位租约、worker提交与报告；复审修复后还覆盖无计划／顺序路径的全局槽位、局部暂停保留独立结果、整合resolver异常恢复、恢复后转人工、干净应用中断后不重跑worker、并发费用上限和硬退出计数重建（含失败编辑消耗）。

本增量未验证：

- 没有真实模型在两个线程上并行调用，也没有真实模型整合修复效果；测试的worker是确定性替身。
- 没有Docker后端的并行子任务验证；线程并发与容器会话组合待测。
- 未验证真实GitHub／GitLab评论、子Issue或草稿PR在并行计划下的端到端效果。
- 暂停时保留worktree、局部阻塞记录和已整合的独立结果，但没有自动续用未提交编辑；答复触发任务说明变化时按M3重规划。
- 冲突修复依赖模型判断，程序只检查索引／标记和最终检查；不能保证语义上完全保留双方功能，需要最终审核和人工批准。
- 实际并发收益、费用和失败率没有和顺序执行做对照；不把机制存在等同于效果更好。

公开验证记录见[增量28](../VALIDATION.md#历史机制验收)。
