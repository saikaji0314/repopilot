# 小任务难度与限额评估

这是面向可信仓库、明确需求的人工评估方法，不是自动调度器或已校准的难度预测模型。普通任务开发样本从[冻结协议](../../evals/swebench/ordinary-20261026.json)开始积累；小样本结果不能代表完整 SWE-bench 或生产成功率。

第一组[真实结果与复盘](../../evals/reports/flask-tasks-20261026.md)已完成：功能局部简单仍可能低估审核和关联回归；配置读取任务本次落在预估区间；路由展示任务实现超出预估。结果同时保留整补丁评分与测试补丁冲突的独立诊断，不把评分接入问题误记成代码回归。

## 开始前判断什么

| 维度 | 需要记录的事实 | 对限额的影响 |
| --- | --- | --- |
| 需求与验收 | 预期行为、兼容承诺、复现步骤；哪些接口细节没有确定 | 信息不足可能应澄清，不能一律靠更多调用解决 |
| 关联范围 | 预计涉及的接口、调用方、测试和文档，而非仅计算仓库总行数 | 关联面越大，调查和回归空间通常越多 |
| 领域知识 | 常规输入校验、I/O 与 CLI，或专门数学、并发、协议知识 | 定位到代码不等于有能力设计正确解法 |
| 环境就绪 | 固定版本、基线公开检查、独立验收控制能否执行 | 环境故障单列；模型不应消耗预算修复未就绪的评测环境 |
| 实施与收尾 | 预计实现、独立验证、审核、一次返工的工作 | 限额覆盖完整流程，不能只估生成补丁 |

先给出低／低到中／中等判断、具体理由和预计阶段调用区间，再配置总模型／工具调用、输出、上下文、时间和估算费用上限。区间只是待检验假设，不是统计置信区间；不同模型、工具与仓库需要重新校准。

当前运行时仍使用共享全局限额，尚未实现阶段预算硬预留。协议中的阶段估计只能用于事后比对，不能描述成程序已经保证审核额度。初次审核与返工次数也应分别记录。

## 结束后如何判断是否匹配

- 分开记录官方补丁验收、固定版本独立检查、审核完成和最终交付；修对但没有完成审核仍是流程未完成。
- 查看实际停止阶段、剩余调用、最大请求体、压缩次数、输出截断、阶段 token／费用及活跃时间；环境安装和下载耗时另外记录。
- 额度提前用完时，先区分反复调查、无效动作、复杂实现和审核空间不足，再决定下一份协议是否调整。不能直接认定“题太难”或“预算太小”。
- 通过但未接近上限，只能说明本次上限足够；不能据此证明可以把上限收紧到本次用量，也不能证明该任务总能成功。
- 同一工具的重复调用可能是必要复查。原样重复计数用于定位轨迹，不直接作为浪费或失败判据。
- 结果不符合预估时保留原判断和全部尝试，解释差异；不事后调低难度、扩大预算或只展示成功重试。

## 标准题与产品任务的边界

SWE-bench 能提供独立修复验收，但历史 Issue 可能没有完整规定最终 API；官方测试不通过后，需要区分实际功能缺陷、回归和接口预期不一致。不能因此修改隐藏验收来提高成绩，也不能让模型事先获得参考补丁。

本地业务需求便于确认验收和完整交付，但必须标注自拟需求、已有解法和合成样例。已在旧 PR 中完成的需求不能再次当作新题。两类任务分别报告，不混合计算一个“成功率”。
