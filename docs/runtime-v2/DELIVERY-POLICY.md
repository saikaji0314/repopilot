# 交付、合并与软件发行的边界

## 默认交付：草稿PR／MR

独立检查与审核通过后，负责人核对完整提交SHA并明确批准，RepoPilot才推功能分支并创建草稿。`publish`表示发布分支和草稿PR／MR，不表示发布软件。回答澄清、批准别的提交或旧的审核结论不能代替本次决定。

## GitHub可选：负责人Approve后受控合并

每个运行显式启用策略，登记负责人、必需检查、目标仓库及分支。通常由GitHub App创建PR，负责人在GitHub将其转为Ready for review，并对当前SHA提交原生Approve。程序核对review身份和版本、CI、分支保护、远端分支与可合并状态，满足条件才提交合并；App不请求绕过规则。

如果启用基线更新，主线改变后程序可合入最新main；文本冲突进入受限修复。更新后重新执行独立检查、双审、推送和CI，再等负责人批准新SHA。旧Approve不能放行新代码。更新次数和模型、工具、费用、时间沿用原运行上限，耗尽后暂停，不自动增加。

合并请求被接受不等于交付完成。程序需重新读取远端结果，确认候选和基线包含在合并提交中，合并提交位于目标主线；重复执行先核对既有副作用。停用自动提交不会撤回已经发送的远端请求，仍需确认结果。[命令和详细规则](MERGING.md)

## 软件发行与部署

软件版本、发行提交、构建制品、远端标签、包上传与部署环境需要另行确定和授权。批准创建PR或合并代码不继承为批准上线。当前没有将软件发行、生产部署、跨仓库联动或merge queue作为自动完成的能力。

## 验证依据

GitHub正常原生Approve与App合并已有真实小任务记录；复杂路径按[验证总览](../VALIDATION.md)区分真实、离线与未验证。GitLab自动合并和其他未明确支持的平台特性不套用GitHub结论。软件发行前另做[预发行检查](PRE-RELEASE.md)。
