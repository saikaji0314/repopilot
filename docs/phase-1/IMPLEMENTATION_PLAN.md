# 第 1 期实施与学习计划

## 1. 实施原则

本期按“先契约和测试、再实现、最后接真实模型”的顺序推进。每一步都必须能单独运行和解释，不一次生成整个 Agent。

建议你在实现前手写一遍 [Agent Loop 伪代码](./AGENT_LOOP_DESIGN.md#5-循环伪代码)。理解实现时，需要讲清楚的不是某个 SDK 方法，而是消息如何变化、工具为何安全、循环为何一定停止。

## 2. 实现顺序

### 步骤 1：配置与协议模型

新增：

- `AgentSettings`：模型、最大步数、工具数、超时、Token、费用和输出上限；
- `AgentStatus`、`StopReason`；
- `ToolResult`、`ModelTurn`、`Usage`；
- `ChatModel` Protocol；
- Agent 专用 Prompt。

先写测试：

- 非法上限不能加载；
- 状态枚举和终止原因可序列化；
- `ToolResult` 拒绝额外字段；
- Agent Prompt 不含“完整仓库快照”或“没有工具”；
- Agent Prompt 不暴露 Oracle 和补丁。

学习检查：能够解释“协议模型”和“SDK 对象”为什么要隔离。

### 步骤 2：路径守卫和三个文本工具

依次实现：

1. `WorkspacePathGuard`；
2. `list_files`；
3. `search_code`；
4. `read_file`。

先写越界、扩展名、行数、结果截断测试，再写正常路径。不要先实现“能读文件”，最后才补安全检查；路径守卫是工具能力的一部分。

学习检查：能够解释为什么 `path.resolve()` 一次还不够，以及符号链接如何造成逃逸。

### 步骤 3：白名单 `run_test`

实现固定 argv 的 pytest 工具，不接受完整命令字符串。

先写测试：

- 合法测试文件和 node ID；
- 额外 pytest 参数被拒绝；
- Shell 操作符被拒绝；
- pytest 失败返回 `ok=true`；
- 进程启动失败和超时返回不同错误码；
- 输出可截断。

学习检查：能够解释“测试失败”和“工具失败”为什么是两类状态。

### 步骤 4：工具注册表

实现工具注册、Schema 导出、参数解析和统一错误转换。

先写测试：

- 工具名重复时启动失败；
- 未知工具安全失败；
- 非法 JSON、缺字段、额外字段安全失败；
- 工具异常不会绕过 Trace；
- Schema 中不出现实现内部参数，如 `workspace_root`。

学习检查：能够从一条 `tool_call` 手动走完“解析—校验—执行—ToolResult—tool message”。

### 步骤 5：用 Fake 模型实现 Agent Loop

Fake 模型按队列返回预设 `ModelTurn`。先实现下列轨迹：

```text
search_code → read_file → run_test → final_answer
```

必须覆盖：

- 正常完成；
- 模型直接给最终答案；
- 未知工具；
- 工具参数错误；
- 工具执行异常；
- 最终 JSON 不合法；
- 最大模型轮数；
- 最大工具次数；
- 总超时；
- Token 或费用达到上限；
- 模型 API 异常。

学习检查：关闭代码后，自己画出每次循环前后 `messages` 新增了什么。

### 步骤 6：轨迹保存

实现 `trace.jsonl`、`messages.json`、`summary.json` 和可选 `final_answer.json`。

测试要求：

- 成功和失败都产生 summary；
- 每个 tool call ID 能对应一个 tool result；
- Trace 事件时间顺序正确；
- 不写入 API Key；
- 工具长输出按配置截断；
- 临时工作区删除后，Trace 仍可独立查看。

学习检查：任选一次失败运行，只读 Trace 就能说明失败发生在哪个边界。

### 步骤 7：接入百炼原生 Tool Calling

扩展模型适配器：

- 输入 `messages` 和工具 Schema；
- 每一轮都传 `tools`；
- 非流式调用；
- 正规化 content、tool_calls、finish_reason 和 usage；
- 不让 Agent Loop 依赖 OpenAI SDK 类型。

只做一次最小真实烟雾测试：让模型在临时工作区调用 `list_files`，观察原始响应是否含标准 `tool_calls`。烟雾测试通过前不跑 6 条评测。

学习检查：能够解释 assistant tool-call message 和对应 `role=tool` message 为什么必须同时进入历史。

### 步骤 8：CLI 与任务编排

CLI 负责：

1. 选择任务；
2. 验证干净仓库；
3. 创建缺陷工作区；
4. 组装工具注册表和 Agent；
5. 运行并打印简短结论；
6. 保存结果；
7. 无论成功失败都清理临时工作区；
8. 根据终态设置进程退出码。

CLI 不包含 Agent 决策逻辑，`scripts/run_agent.py` 保持薄包装。

### 步骤 9：里程碑评测

顺序固定：

1. `flaskr-auth-001` 一次真实运行；
2. 人工检查工具轨迹、最终答案、Token 和费用；
3. 修复基础设施问题；
4. 六个任务各运行一次；
5. 按第 0 期相同 Oracle 人工评分；
6. 生成 Phase 1 对比报告。

不要在每次小修改后跑完整真实评测。工具和循环逻辑使用 Fake 模型回归，只有里程碑调用真实 API。

## 3. 分阶段实施

### 工具层里程碑

- 上午：协议模型、配置、Prompt、路径守卫；
- 下午：四个工具及其单元测试；
- 晚上：写当日理解记录，手动画一次工具调用消息序列。

本阶段可验收结果：四个工具可以被普通 Python 代码安全调用，不需要模型。

### Agent 闭环里程碑

- 上午：工具注册表、Fake 模型、Agent Loop；
- 下午：Trace、真实模型适配、CLI、单任务烟雾测试；
- 晚上：6 任务评测、对比报告与复盘。

本阶段可验收结果：CLI 能完成至少 4/6，异常轨迹可解释，费用可统计。

如果工具层没有通过安全测试，应先补齐安全验证，再接入真实 API 和完整评测；不能用任意 Shell 替代受控工具。

## 4. 预算计划

第 0 期平均单次调用约 ¥0.0316。Agent 每个任务预计产生 3～6 次模型调用，但每轮上下文会增长，因此只做数量级估算：

| 用途 | 计划调用 | 预估费用 |
| --- | ---: | ---: |
| Tool Calling 烟雾测试 | 1～2 次 | < ¥0.10 |
| 单任务端到端调试 | 3～6 次模型调用 | 约 ¥0.10～0.30 |
| 6 任务里程碑评测 | 约 18～36 次模型调用 | 约 ¥0.60～2.00 |
| 第 1 期预留上限 | - | ¥5.00 |

真实费用由 usage 计算，不以此表替代运行时限制。建议单任务默认限制：最多 10 个模型轮次、12 个工具调用、120,000 累计 Token、¥1.00 估算费用和 10 分钟墙钟时间。

## 5. 评测表

Phase 1 报告至少包含：

| 维度 | 指标 |
| --- | --- |
| 正确性 | 分数通过、硬条件满足、严格通过 |
| 证据 | 正确文件/函数证据、真实测试证据 |
| Agent 行为 | 模型轮数、工具调用数、各工具分布 |
| 可靠性 | 工具成功率、协议错误、限制停止次数 |
| 效率 | 墙钟时间、模型耗时、Token、费用 |
| 稳定性 | 是否循环、是否重复读取、是否过早结束 |

与第 0 期对比时必须同时展示收益和代价。例如：严格通过率提高，但调用次数、耗时和费用也增加。

## 6. 理解债清单

以下问题有任意一个讲不清，就暂时不要进入第 2 期：

1. Tool Calling 与让模型输出一段 JSON 命令有什么区别？
2. 为什么工具参数必须在主程序再次校验，不能相信模型生成的 Schema 参数？
3. assistant 的 `tool_calls` 和 `role=tool` 的结果消息如何通过 call ID 配对？
4. 为什么测试返回码 1 不等于工具调用失败？
5. 最大步数、工具数、超时、Token 和费用限制分别防什么问题？
6. 为什么 Agent Prompt 不能复用第 0 期基线 Prompt？
7. 为什么不向模型暴露完整仓库快照？
8. Trace 如何在不记录隐藏思维链的情况下提供可解释性？
9. Fake 模型测试证明了什么，又没有证明什么？
10. 如果 Agent 得分没有超过单次 LLM，这一期是否仍有价值，为什么？

第 1 期复盘应逐项写出自己的答案，不复制模型解释。
