## 3. 被测仓库的最低要求

为了让评测结果可复现，首个被测仓库应满足：

- 无硬件、传感器、GPU 或专用算力依赖；
- 能在本机运行，优先选择不依赖外部服务的项目；
- 如果依赖数据库或缓存，必须能用 SQLite、Fake 或测试夹具替代；
- 安装和运行过程明确，最好 10 分钟内可以完成；
- 有自动化测试，或者能以较小改动补出确定性的测试；
- 项目规模较小，但至少有多个模块和真实业务分支；
- 有明确的开源许可证，允许学习、修改和公开展示；
- 不含真实密钥、个人数据或公司内部信息；
- 能构造至少 6 条互不重复的分析任务。

## 4. 仓库组织原则

RepoPilot 是“Agent 系统”，被测 Python 项目是“Agent 操作的目标”。两者必须在概念和代码上分离：

```text
repopilot/
├── PROJECT_GOAL.md
├── docs/                   # RepoPilot 的设计和学习记录
├── repopilot/              # 后续实现的 Agent 代码
├── evals/                  # 任务数据、评分器和基线结果
├── target-repos/           # 主被测仓库的干净基线
│   └── flaskr-tutorial/    # Flask 官方教程应用 3.1.3
└── flaskDemo/              # 保留的第二静态分析案例，不放 Agent 代码
```

如果后续公开 RepoPilot 仓库，需要根据被测项目的许可证决定使用 Git submodule、下载脚本、补丁文件，还是只记录上游提交哈希，不能默认把第三方源码一并重新发布。

## 5. 正式任务的建议分布

主仓库确定后，首批 6 条任务建议覆盖：

| 类型 | 数量 | 目的 |
| --- | ---: | --- |
| 测试失败定位 | 2 | 检查 Agent 是否能从失败信息追到实现代码 |
| 明确缺陷分析 | 2 | 检查根因、证据和修复计划质量 |
| 输入校验或边界条件 | 1 | 检查对分支和边界条件的理解 |
| 配置或依赖问题 | 1 | 检查跨文件检索和运行环境判断 |

第 0 期的基线只要求“分析”，不允许修改文件。第 3 期加入人工审批后，再把其中部分任务升级为可执行修复任务。

## 6. 第 0 期执行顺序

1. 评估 `flaskDemo`，决定保留、改造还是更换；
2. 固化任务字段和输出字段；
3. 为选定仓库编写 6 条正式任务及评测者答案；（已完成）
4. 人工运行每条任务，确认输入信息足够且答案可验证；（已完成）
5. 按 [基线模型决策](./MODEL_BASELINE.md) 实现单次 LLM 基线脚本；（已完成）
6. 先运行 1～2 条任务估算单次费用；
7. 再运行完整基线，生成结果表和失败分类；
8. 完成本期复盘，之后才进入 Agent Loop。

## 7. 本期完成标准

第 0 期只有同时满足以下条件才完成：

- 已确定 1 个主被测仓库及固定版本；
- 已有 6 条机器可读、可重复执行的正式任务；
- 每条任务都分离了 Agent 可见输入和评测者答案；
- 每条任务都有硬性条件和量化评分规则；
- 单次 LLM 基线能够用一条命令运行；
- 基线报告包含正确性、证据质量、耗时、Token、费用和失败类型；
- 已测算后续完整评测次数不会突破 200 元总预算。
