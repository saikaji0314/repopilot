# 桌面版需求与验收草案

状态：2026-10-30 需求与已确认视觉基线，执行详情开发切片已落地，完整桌面应用尚未完成。现有能力、桌面新增要求和待验证效果分别列出，不以界面预览代表真实功能。实际完成、验证和限制见 [实现与验证](IMPLEMENTATION.md)。

## 产品目标

提供 Windows 上的本机研发任务工作台。接入 GitHub 仓库后，新 Issue 自动入队并执行；使用者能实时查看每个 Agent 的实际工具动作、参数、结果、命令输出和代码改动，并在同一应用中创建 Issue、参与讨论、回答问题、追加需求及批准交付。

应用参考 Jenkins 经典任务工作台的信息组织：仓库与任务列表、队列、执行器、执行历史、控制台输出、阶段概览和结果入口。保留 RepoPilot 的需求澄清、代码证据和人工审批语义。不使用 Jenkins 商标、吉祥物或品牌资产作为 RepoPilot 身份。

“自动开始”以仓库已登记本机目录、检查配置、模型与预算、服务在线为前提；无运行空位时排队。登记仓库时确定新 Issue 接纳起点，历史 Issue 不默认回扫。此规则不授予自动批准或绕过版本校验的能力。

## 任务与并发模型

区分三个层次，UI 分别展示：

1. Issue 运行数：全局／单仓库任务调度上限；首版默认 2／2。
2. 单 Issue 内的子任务：由计划判断是否可并行；依赖未满足则等待；每个实现子任务独立工作区。
3. Agent 角色：规划、实现、独立检查和双视角审核等；阶段顺序不等于所有角色始终并发。

Issue 运行数和实现槽位是不同限制。现有运行时实现槽位全局最多 2 个，不能将两个 Issue 各自显示成可无限启动 Agent。桌面服务必须共用调度状态和槽位；资源不足显示排队与原因，避免依靠额外进程或运行目录突破上限。

降低并发设置时不强杀已运行任务，只约束后续派发。同仓库不同 Issue 的独立 worktree 允许并行开发；候选交付仍核对最新基线，分别重新验证和审核，不承诺两个 PR 没有业务或文本冲突。

## 可观察的实际动作

阶段条只作导航。任务详情至少包含：

- 当前运行、尝试、子任务、Agent 身份、角色、worktree 和最近活动时间。
- 工具名称、关联动作 ID、经脱敏的参数；读取文件显示路径和行范围，搜索显示查询和命中，编辑显示文件及实际 diff。
- 命令显示登记检查、实际 argv、工作目录、开始时间、持续输出、耗时、最终退出码与超时／中断原因。
- 模型请求期间显示等待模型响应及耗时；没有可展示内容时明确等待，不生成虚构进度或思考。
- 失败、返工、需求变更、基线更新和旧批准失效均保留记录；不同 Agent 的输出可区分。
- 断连显示状态待核对和最近确认时间；重连以快照与补读事件恢复，无重复或静默缺口。

输出需要有界缓存、分块、截断说明和原始产物入口；脱敏在进入前端前完成。现有工具开始／完成记录可复用，但仍需稳定关联标识、跨进程事件协议和运行中的输出推送，不能把完成后一次性显示结果称为实时控制台。

## 评论、正式答复与需求变更

用户层面保留“普通评论”和“回复 Agent”两个入口；回复 Agent 中区分“回答问题”和“追加／变更需求”。

桌面端点击对应入口，自动携带当前 Issue、运行、请求／需求版本和引用，不要求用户手写机器标记。GitHub 网页评论以真实机器人账号的 @提及配合明确引用／命令关联；具体语法仍需实现设计和真实平台验证。仅出现 @ 不直接等同于某个问题已回答或某次发布已批准。

正式输入校验登记负责人身份、来源、评论 ID 和版本；重复轮询不重复采纳。普通评论不能因恰好写在提问之后就被吸收为答案。对错误、过期或无法唯一关联的输入明确回执，不猜测目标任务。

有效答复自动继续同一运行及累计预算。运行中追加需求按以下过程处理：

1. 保存来源与变更意图，立即显示“已收到，等待当前操作结束”；停止受影响分支在旧需求下派发新的工具动作。
2. 当前在途操作到安全边界后核对并保存现场；不声称已取消不能取消的工具或远端副作用。
3. 更新需求版本，保留旧计划、已产生的改动和证据；重新规划，核对可复用部分。
4. 根据新需求重新检查、审核，旧批准不能用于新版本；新的人审要求明确展示。预算与运行身份不清零，不另起并行重复任务。

已合并／已结束的历史运行收到新需求时不能伪装成继续原有在途运行；需要明确的后续任务或新尝试流程，该语义后续细化，不纳入首轮运行中变更的承诺。

普通评论、需求答复和 @ 需求变更均不能替代固定 SHA 发布批准或 GitHub 原生 Approve。

## 人工交付操作

发布批准展示候选提交、需求版本、diff、独立检查和审核依据，确认后由执行身份发布。原生 PR 审核展示当前 head 和本人身份，由用户明确操作；平台记录回读后才记为审核成功。

原生审核成功、合并请求被平台接受、最终合并已确认是不同状态。沿用现有分支保护、版本失效、CI、负责人身份和合并核对规则。机器人安装身份与本人授权身份分离。

## 接口与技术方案候选

设计基线沿用 Electron + React／TypeScript／Vite，Python runtime 保留；FastAPI 提供本机查询和操作接口，SSE 推送事件，现有 SQLite 与产物持久化。具体打包方式、库版本和 Windows 进程管理需通过实现探针确定，尚未发布安装包。

桌面与 CLI 共享业务规则，不解析人类可读 CLI 输出重建业务状态；前端不直接写 jobs 数据库。UI、服务与执行 worker 分离；关闭窗口不等同于退出服务。电脑关机／休眠后不能承诺继续运行；异常恢复核对现场，不自动透明重放副作用。

## 当前已有与新增范围

| 能力 | 当前事实与新增工作 |
| --- | --- |
| 多 Issue 调度 | 已有全局和单仓库各 1–4 的可配置机制，当前默认 1／1；新版采用 2／2 默认并提供 UI 配置 |
| 单 Issue 并行实现 | 已有计划、独立 worktree、全局最多 2 个实现槽位和串行整合；真实模型并发效果尚未完整验证 |
| 双视角审核 | 已有并行审核固定候选的机制及真实小任务交付记录；不能据此认定所有角色都会同时运行 |
| 工具事件 | 已有工具开始／结束与结果；需补可消费接口、关联 ID、流式命令输出和断线补读 |
| 评论问答 | 已有提问投递和登记负责人回复采纳；当前按提问后首条有效评论选择，没有 @路由或普通／正式分类；需升级协议并验证真实往返 |
| 运行中需求变更 | 属于新增流程；不能将已有等待澄清时的答复恢复等同于随时安全接纳新需求 |
| 人工操作 | 已有 CLI 固定提交批准和原生审核检测；桌面登录、创建 Issue、分类评论和提交原生审核需要新增与验证 |
| 桌面生命周期 | 托盘、独立服务、安装包和升级均为新增；现有前台监听不等同于已实现桌面后台服务 |

## 验收对应关系

| 要求 | 需保留的验证证据 |
| --- | --- |
| D-02 | 桌面和 GitHub 网页各创建新 Issue，均自动入队／执行；重复发现不重复启动；历史 Issue 不误扫 |
| D-03、D-04 | 同仓库两个 Issue、跨仓库两个 Issue 分别并发；第三个排队；验证两层上限及设置调整；独立工作区与累计用量不混用 |
| D-05、D-06 | 对照实际 Agent 事件、文件 diff、命令输出；长命令结束前可见输出；并行事件正确归属；失败和返工可追溯 |
| D-07、D-08 | 问题之后先发普通评论不得恢复，显式答复才恢复；过期、重复、其他身份和错误问题关联分别校验；有真实平台记录 |
| D-09 | 工具在途时接收需求变更，回执可见；安全保存现场并重规划；保留已完成改动、旧证据和用量；旧批准失效且不产生重复运行 |
| D-10 | 应用内固定 SHA 批准、平台本人原生审核与最终合并分别回读确认；错误版本拒绝；平台写入超时先查询再决定是否重试 |
| D-11 | 关闭主窗口后同一受限任务继续，托盘重开可补读；显式退出与异常退出分别验证；断连不能显示陈旧健康状态 |
| D-01、D-12 | 独立 Windows 环境安装／启动／登录；diff 可查看并可打开外部编辑器；包内不含开发机凭证和运行数据 |
| D-13、D-14 | 拖动、键盘、折叠、重启记忆与运行目录切换；真实 Windows 加密后恢复；凭证不出现在 API 响应、明文文件与校验错误；评论超时核对、重复发送和错误身份分别验证 |

确定性模型和模拟平台用于机制回归。真实 GitHub 操作、真实模型并发、运行中变更效果、长期托盘运行和安装体验须分别实测；尚未通过前不能标为已验证。
